# ベンチマーク・性能評価レポート

本ドキュメントでは、[`Google SentencePiece Lite`](https://google.github.io/sentencepiece/lite/) および ONNX Runtime を用いた軽量推論環境（本実装）と、標準的な `transformers` + `PyTorch` 構成との性能比較検証結果をまとめます。

---

## 1. トークナイザー単体性能（前処理スループット）

日本語テキスト 10,000 件を連続でトークナイズした際の所要時間、スループット（処理件数/秒）、および 1 件あたりの平均レイテンシを測定しました。

### 測定結果 (10,000 件)

| トークナイザー実装 | 10,000 件所要時間 | スループット (Throughput) | 1件あたり平均レイテンシ | 高速化倍率 |
|---|---|---|---|---|
| **Hugging Face Fast Tokenizer** (Rustベース) | 455.03 ms | 21,976.5 sent/s | 45.50 µs | 1.0x (基準) |
| **SentencePiece Lite (本実装)** (C++20 Zero-copy mmap) | **33.97 ms** | **294,395.5 sent/s** | **3.40 µs** | **約 13.4 倍 高速** ⚡ |

### 技術的解説
* **Zero-copy mmap**: FlatBuffers 形式（`.spm.fb`）を採用することで、ファイルからのメモリコピーおよびパースオーバーヘッドを完全に排除しています。
* **CPU ボトルネックの解消**: GPU 推論環境であっても前処理（トークナイズ）は CPU が担当するため、従来構成ではトークナイズ待ち（GPUの遊休）が発生していました。SentencePiece Lite により 1 文わずか **3.4 マイクロ秒** で処理され、大規模バッチ処理時でも CPU 前処理がボトルネックになりません。

## 3. End-to-End 埋め込み推論性能（テキスト入力からベクトル出力まで）

前処理（トークナイズ）→ モデル推論 → Mean Pooling → L2正規化 までを網羅した、エンドユーザーが実際に呼び出す `encode()` 関数の総合処理性能です。

### A. 単一クエリのレイテンシ比較 (30m / CPU)
WebAPIや検索サービスで一般的な「1リクエスト1クエリ」の即時応答性（レイテンシ）を測定しました。

| 実装 | 単一クエリ応答時間 (レイテンシ) | 高速化倍率 |
|---|---|---|
| **PyTorch 2.14 (Transformers)** | 6.03 ms | 1.0x (基準) |
| **RuriV3Lite (本実装)** | **2.94 ms** | **約 2.05 倍 高速** ⚡ |

> **解説**: 小バッチ・単一クエリ処理では、PyTorch/TransformersのPythonレイヤー（テンソル生成・動的型チェック・ディスパッチ）のオーバーヘッドが支配的になります。本実装は C++20 の SentencePiece Lite と C++ ONNX Runtime が直結しているため、Python オーバーヘッドを最小限に抑え **3ms 未満の超低遅延** を実現します。

### B. バッチ処理性能（100文 / Batch=32 / CPU）
全モデルサイズにおけるスループット測定結果です。

| モデルサイズ | 次元数 | PyTorch 2.14 CPU | RuriV3Lite (本実装) CPU | 特徴・推奨用途 |
|---|---|---|---|---|
| **30m** | 256 | 233 ms (429.3 sent/s) | 369 ms (271.1 sent/s) | 最速・低メモリ、エッジやサーバーレスに最適 |
| **70m** | 384 | 584 ms (171.1 sent/s) | 724 ms (138.1 sent/s) | バランス型、一般的な文書類似度検索 |
| **130m** | 512 | 1,551 ms (64.5 sent/s) | 2,137 ms (46.8 sent/s) | 高精度ベクトル検索 |
| **310m** | 768 | 3,417 ms (29.3 sent/s) | 4,615 ms (21.7 sent/s) | 最高精度・研究・高難度タスク |

### C. GPU推論（CUDA / Tensor コア）
* **GTX 1060 / 1080 (Pascal CC 6.1)**: 最新の PyTorch / ONNX Runtime (CUDA 12/13) では Pascal アーキテクチャのカーネル提供が終了しているため、自動判定により安全に CPU 実行へフォールバックします。
* **RTX 3060 / 4090 / A100 (Turing/Ampere/Hopper CC ≥ 7.0)**: `model_fp16.onnx` が自動選択され、Tensor コアによる半精度（FP16）演算が有効化されます。CPU比で **約 5〜10倍以上のスループット向上** および **VRAM消費の半減（30m: わずか 71MB）** を発揮します。

## 4. ハードウェア適応型推論（Pascal vs Ampere以降）

本リポジトリのラッパー（`ruri_v3_lite.py`）は、実行環境の GPU 世代（CUDA Compute Capability）を `ctypes` 経由で自動判別します：

| 実行環境 | アーキテクチャ | 選択されるモデル | 最適化の理由 |
|---|---|---|---|
| **CPU のみ** | x86_64 / ARM | `model.onnx` (FP32) | CPU ネイティブ演算 |
| **GTX 1080 / 1060** 等 | Pascal (CC 6.1 < 7.0) | `model.onnx` (FP32) | Pascal 世代は FP16 演算器が弱く、FP32 の方が高速 |
| **RTX 3060 / 4090 / A100** 等 | Ampere / Hopper (CC ≥ 7.0) | `model_fp16.onnx` (FP16) | Tensor コアの活用により **スループット大幅向上・VRAM消費半減** |

## 6. コード規模・バイナリサイズ・パッケージ容量評価

SentencePiece Lite および Zero-Torch 構成がもたらす最大の利点は、**「極限まで無駄を削ぎ落としたフットプリント（Footprint）」** です。コンテナイメージの軽量化、サーバーレス環境（AWS Lambda / Cloud Run）でのコールドスタート短縮、エッジデバイスへの展開において絶大な効果を発揮します。

### A. ランタイム・インストールパッケージ容量の比較 (Disk Footprint)
推論実行に必要な Python パッケージ全体のディスク占有サイズです。

| 構成要素 | 従来の標準構成 (PyTorch + Transformers) | 本実装 (Zero-Torch 構成) | 削減率 |
|---|---|---|---|
| **ディープラーニング基盤** | `torch`: **約 1,120 MB (CPU) / 約 3,500 MB (CUDA)** | `onnxruntime`: **約 40 MB (CPU) / 約 320 MB (GPU)** | **70% 〜 90% 削減** |
| **モデルローダー・抽象化** | `transformers`: **約 52 MB** | 不要 (0 MB) | **100% 削減** |
| **トークナイザー** | `sentencepiece`: **約 10 MB** | `sentencepiece_lite`: **約 1.7 MB (Wheel)** | **83% 削減** |
| **数値演算** | `numpy`: **約 57 MB** | `numpy`: **約 57 MB** | 同等 |
| **総インストール容量 (CPU)** | **約 1,240 MB (~1.2 GB)** | **約 100 MB** | **🔥 92% 削減** |
| **総インストール容量 (GPU)** | **約 3,600 MB (~3.6 GB)** | **約 380 MB** | **🔥 89% 削減** |

### C. コードベース規模と保守性 (Lines of Code)

| 項目 | 従来構成 (PyTorch / Transformers / Hugging Face) | 本実装 (`ruri_v3_lite.py`) | 利点 |
