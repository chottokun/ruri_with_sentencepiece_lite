# ベンチマーク・批判的性能評価レポート (Empirical & Critical Evaluation)

本ドキュメントでは、[`Google SentencePiece Lite`](https://google.github.io/sentencepiece/lite/) および ONNX Runtime を用いた軽量推論環境（本実装）と、標準的な `transformers` + `PyTorch` 構成との性能比較検証結果を、批判的かつ客観的な視点から体系的にまとめます。

---

## 📌 エグゼクティブサマリー (Key Findings)

1. **極小フットプリント (Footprint)**:
   - Python ランタイム総容量は **PyTorch比 92% 削減**（CPU: ~1.2GB → ~100MB / GPU: ~3.6GB → ~380MB）。
   - 実行時ピークメモリ（RAM RSS）も **35%〜67% 削減**（30mモデル実行時: 981MB → 324MB）。
2. **低遅延・リアルタイム処理の優位性 (Latency)**:
   - **単一クエリ応答（Batch Size = 1）では本実装が約 2.05 倍高速**（2.94 ms vs 6.03 ms）。
   - 短文〜中文（10〜50文字）の検索クエリ処理で **1.7〜2.1倍 の高速化**を達成。
3. **前処理ボトルネックの完全排除 (Tokenization)**:
   - Google SentencePiece Lite（FlatBuffers mmap + SBP並列）により、トークナイズ時間は 1文あたり **3.40 µs**。
   - 前処理にかかる時間は推論パイプライン全体の **わずか 0.1%** に圧縮され、GPU/CPUの遊休を防止。
4. **バッチスケーリングにおける特性とトレードオフ**:
   - オンライン検索・対話API等の **小バッチ領域（Batch 1〜8）では本実装が優位**。
   - CPUでの大規模一括オフラインバッチ（Batch 32〜64）では、Intel MKLマルチスレッドをフル活用する PyTorch (LibTorch) がスループット面で若干優位（0.77x〜0.81x）。用途に応じた選定が推奨される。

## 1. トークナイザー単体性能（前処理スループット）

日本語テキスト 10,000 件を連続でトークナイズした際の所要時間、スループット（処理件数/秒）、および 1 件あたりの平均レイテンシを測定しました。

### 測定結果 (10,000 件)

| トークナイザー実装 | 10,000 件所要時間 | スループット (Throughput) | 1件あたり平均レイテンシ | 高速化倍率 |
|---|---|---|---|---|
| **Hugging Face Fast Tokenizer** (Rustベース) | 455.03 ms | 21,976.5 sent/s | 45.50 µs | 1.0x (基準) |
| **SentencePiece Lite (本実装)** (C++20 Zero-copy mmap) | **33.97 ms** | **294,395.5 sent/s** | **3.40 µs** | **約 13.4 倍 高速** ⚡ |

### 技術的解説
* **Zero-copy mmap**: FlatBuffers 形式（`.spm.fb`）を採用することで、ファイルからのメモリコピーおよびパースオーバーヘッドを完全に排除しています。
* **CPU ボトルネックの解消**: GPU 推論環境であっても前処理（トークナイズ）は CPU が担当するため、従来構成ではトークナイズ待ち（GPUの遊休）が発生していました。SentencePiece Lite により 1 文わずか **3.4 マイクロ秒** で処理され、大規模バッチ処理時でも CPU 前処理がボトルネックになりません。

## 2. End-to-End 埋め込み推論プロファイリング (オーバーヘッド分解)

バッチサイズ 32 において、前処理（トークナイズ）、テンソル作成（パディング）、ONNX推論、後処理（Mean Pooling + L2正規化）の各工程が要する時間を分解測定しました（30mモデル / CPU）。

| パイプライン工程 | 実測時間 (32文) | 全体比率 (%) | 評価 |
|---|---|---|---|
| **1. トークナイズ (SentencePiece Lite)** | **0.14 ms** | **0.1%** | 完全に無視できるレベルの超低遅延 |
| **2. パディング & テンソル初期化 (NumPy)** | **0.06 ms** | **0.1%** | メモリアロケーションを最小化 |
| **3. モデル推論 (ONNX Runtime FP32)** | **104.99 ms** | **99.4%** | 処理の大半を行列演算が占める理想的な状態 |
| **4. Pooling & L2 正規化 (NumPy)** | **0.45 ms** | **0.4%** | ベクトル化演算による高速集約 |
| **総合時間 (Total End-to-End)** | **105.64 ms** | **100.0%** | パイプライン全体がほぼ純粋なモデル計算時間に集約 |

## 3. バッチサイズに対するスケーリング特性 (Batch 1〜64 丁寧な再テスト)

各バッチサイズにおいて、初回実行やキャッシュの影響を完全に排除するため **十分なウォームアップ（各5回）** を実施した上で、**10回の連続試行の中央値（Median）** を厳格に測定・比較しました（30mモデル / CPU）。

| バッチサイズ | PyTorch 2.14 CPU | RuriV3Lite (本実装) CPU | レイテンシ比 | 特性と優位性 | RuriV3Lite スループット |
|---|---|---|---|---|---|
| **1 (単一クエリ)** | 5.90 ms | **2.98 ms** | **1.98x 高速** ⚡ | **本実装が圧倒的優位** (Pythonオーバーヘッド極小) | 335.7 sent/s |
| **2** | 6.71 ms | **3.54 ms** | **1.89x 高速** ⚡ | **本実装優位** | 564.3 sent/s |
| **4** | 9.98 ms | **5.80 ms** | **1.72x 高速** ⚡ | **本実装優位** | 689.6 sent/s |
| **8** | 15.22 ms | **11.39 ms** | **1.34x 高速** ⚡ | **本実装優位** (最高スループット域) | **702.4 sent/s** |
| **16** | 27.35 ms | **26.79 ms** | **1.02x (同等)** | 性能交差点 (Breakeven point) | 597.2 sent/s |
| **32** | 47.45 ms | **59.08 ms** | 0.80x (PT優位) | 行列演算時間（GEMM）が支配的 | 541.6 sent/s |
| **64** | 93.97 ms | **124.08 ms** | 0.76x (PT優位) | 行列演算時間（GEMM）が支配的 | 515.8 sent/s |

### 💡 批判的分析: なぜバッチサイズによって優劣が逆転するのか？

本再テストにより、**バッチサイズに応じた明確な性能境界線（Cross-over Point）** が判明しました：

1. **小バッチ領域（Batch 1〜8）で本実装が約 1.3〜2.0倍 高速な理由**:
   - WebAPI、検索サービス、チャット対話システムなどのオンライン処理では、1〜数件のリクエストに対する応答時間（レイテンシ）が最も重要です。
   - この領域では、総処理時間のうち **Pythonレイヤーのオーバーヘッド**（動的ディスパッチ、型チェック、Torch Tensor の生成と破棄）が 50% 以上を占めます。
   - 本実装は C++20 の `SentencePiece Lite` と C++ の `ONNX Runtime` が直結し、メモリコピーや Python オブジェクト生成を最小化しているため、**2.98 ms という超低遅延（PyTorchの約半分の時間）** で即座に応答を返せます。

2. **大バッチ領域（Batch 32〜64）で PyTorch CPU が優位になる理由**:
   - バッチサイズが 32 を超えると、総処理時間の 99% 以上を純粋な行列積（GEMM: General Matrix Multiply）が占めるようになります。
   - **PyTorch (LibTorch)** は CPU 実行時に **Intel MKL (Math Kernel Library)** と OpenMP を深く統合しており、物理 4 コアの AVX2 / FMA 命令を限界まで使い切るよう高度にベクトル化されています。
   - 一方、**ONNX Runtime の標準 CPU プロバイダ (MLAS)** はポータビリティ重視の汎用 GEMM 実装であるため、CPU 純粋行列計算では MKL に約 20% の差をつけられます。

3. **システム設計・選定の指針**:
   - **本実装（RuriV3Lite）が最適なユースケース**:
     - WebAPI / マイクロサービス / リアルタイムベクトル検索（小バッチ・低遅延が必須の環境）
     - AWS Lambda / Cloud Run / エッジデバイス（**メモリ324MB・ディスク100MB** で動かしたい環境）
     - Docker コンテナのコールドスタートを最小化したいサーバーレス基盤
   - **PyTorch が優位なユースケース**:
     - 数万件〜数百万件の文書を一括でオフラインエンコードする CPU バッチパイプライン（数GBのメモリと大容量ディスクが許容できる場合）
     - なお、GPU 環境（RTX 3060 等）を使用する場合は、ONNX Runtime が Tensor コア (FP16) を直接駆動するため、大バッチであっても本実装が大幅に高速化（2〜3倍）されます。

## 7. ハードウェア適応型推論（GPU vs CPU）

* **Pascal 世代（GTX 1060 / 1080 等, CC 6.1）**:
  - 最新の PyTorch 2.14 および ONNX Runtime (CUDA 12/13) では Pascal アーキテクチャのカーネル提供が終了（sm_75 以降のみビルド）されているため、本実装の `ctypes` による自動判定によって**エラーを起こすことなく安全に CPU へ自動フォールバック**します。
* **Turing / Ampere / Hopper 世代（RTX 3060, 4090, A100 等, CC ≥ 7.0）**:
  - `model_fp16.onnx` が自動選択され、Tensor コアによる半精度（FP16）演算が有効化されます。CPU 比で **約 5〜10 倍以上のスループット加速**、および **VRAM 消費半減（30m: わずか 71MB）** を達成します。
