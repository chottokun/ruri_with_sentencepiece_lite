# ruri-v3-reranker-310m 包括的ベンチマーク & 批判的考察レポート

本文書では、日本語最新の高精度 Cross-Encoder リランカーモデル [`cl-nagoya/ruri-v3-reranker-310m`](https://huggingface.co/cl-nagoya/ruri-v3-reranker-310m)（ModernBERT-Ja アーキテクチャ、315M パラメータ）に対する、**Zero-Torch（SentencePiece Lite + ONNX Runtime）実装の性能・数学的等価性・リソース消費・アーキテクチャ境界における批判的考察** を報告します。

---

## 1. 測定環境

- **CPU**: AMD Ryzen / Intel x86_64 (Linux 64-bit, 4 スレッド測定)
- **Base Model**: `cl-nagoya/ruri-v3-reranker-310m`
- **ゼロ・トーチラッパー**: `RuriV3RerankerLite` (`dist_assets/ruri_v3_reranker_lite.py`)
- **トークナイザー**: `sentencepiece_lite` 0.1.0 (FlatBuffers `.spm.fb`)
- **推論エンジン**: `onnxruntime` 1.20.1 (FP32 ONNX opset 17)
- **比較対象**: `torch` 2.14.0 + `transformers` 4.49.0 (`AutoModelForSequenceClassification` + `AutoTokenizer`)

---

## 2. ベンチマーク実測結果

### (1) コールドスタート & メモリ消費 (Threads=4)

| 評価指標 | 公式 PyTorch (Transformers) | Zero-Torch (RuriV3RerankerLite) | 比較・優位性 |
| :--- | :--- | :--- | :--- |
| **モデルロード時間** | 5,456.0 ms | **4,534.3 ms** | **1.20x 高速** |
| **環境インストール容量** | 約 2.5 GB 超 (Torch + CUDA libs) | **約 70 MB** (Wheel + ORT) | **約 97% 削減** |
| **プロセス最大 RSS** | 2,392.3 MB | 3,126.9 MB | アリーナ拡張による確保 |

> **批判的考察**:
> ONNX Runtime の CPUExecutionProvider はスレッドごとのアロケータプール（Arena）を積極確保するためプロセス RSS は同等〜やや多めになりますが、**「コンテナイメージサイズ / インストールフットプリント」は 2.5GB から数十MBへと劇的に削減**され、AWS Lambda や Cloud Run 等のエッジ・サーバーレス環境におけるデプロイ容易性とコールドスタート速度が大きく向上します。

### (2) RAG Top-N リランキングレイテンシ & スループット (Threads=4, 中文 150文字)

実務の RAG（検索拡張生成）におけるベクトル検索後の候補文書 Top-$N$ 件に対する精密リランキング測定結果です。

| 候補件数 (N) | PyTorch E2E (ms) | Lite E2E (ms) | 高速化倍率 | Lite スループット | トークナイズ単体高速化 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Top-5**   | 567.3 ms | **540.4 ms** | **1.05x 高速** | **9.3 docs/s** | **4.24x 高速** |
| **Top-10**  | 1,104.7 ms | 1,277.4 ms | 0.86x | 7.8 docs/s | **4.51x 高速** |
| **Top-20**  | 2,343.2 ms | 2,479.5 ms | 0.95x | 8.1 docs/s | **4.18x 高速** |
| **Top-50**  | 5,828.6 ms | 6,215.3 ms | 0.94x | 8.0 docs/s | **3.79x 高速** |
| **Top-100** | 11,214.4 ms | 12,452.8 ms | 0.90x | 8.0 docs/s | **4.55x 高速** |

> **批判的考察**:
> - **前処理（トークナイズ）**: `sentencepiece_lite` による C++ ゼロコピーペアトークナイズは、Python ラッパーの `AutoTokenizer` に対して **一貫して 3.8x 〜 4.5x 高速** です。
> - **推論計算（BLAS）**: 315M パラメータモデルの CPU 行列積において、PyTorch（Intel MKL/OneDNN 最適化）と ONNX Runtime（MLAS）はほぼ互角の性能を示します。短文・小バッチ（Top-5）ではトークナイズ短縮とディスパッチオーバーヘッドの少なさから Lite が勝利し、大バッチでは PyTorch が僅かに先行します。

## 5. アーキテクチャ境界における批判的考察

### 💡 なぜ「Bi-Encoder + Cross-Encoder」の 2段階構成が必須なのか？

実測値から明らかな通り、315M パラメータの Cross-Encoder は CPU 4スレッド環境で **1秒間に約 8 ドキュメント** を処理します。
- Top-10 のリランキング: **約 1.2 秒**
- Top-50 のリランキング: **約 6.2 秒**
- Top-100 のリランキング: **約 12.5 秒**

もし数千〜数万件のコーパスに対して最初から Cross-Encoder を適用しようとすれば、数十分〜数時間のレイテンシとなり、リアルタイム Web 検索・チャットボットでは実用に耐えません。

| 手法 | 代表モデル | 検索計算量 | メリット | デメリット |
| :--- | :--- | :--- | :--- | :--- |
| **Bi-Encoder (埋め込み)** | `ruri-v3-30m-lite`<br>`ruri-v3-310m-lite` | $O(1)$ (事前インデックス + ベクトル内積) | 数百万件から **数ミリ秒** で候補を抽出可能 | 単語間の詳細な相互文脈・否定関係の見落とし |
| **Cross-Encoder (リランカー)** | `ruri-v3-reranker-310m-lite` | $O(N)$ (リクエスト毎の全結合推論) | 全レイヤーで Query と Doc が Cross-Attention するため **圧倒的な精度** | 候補件数 $N$ に比例して推論コストが増加 |

### 🚀 実務におけるベストプラクティス設計
1. **第 1 段階 (粗選定)**: `ruri-v3-30m-lite` で数万件の文書から高速に **Top-20〜30 件** を絞り込む (レイテンシ: < 10ms)
2. **第 2 段階 (精密選定)**: `ruri-v3-reranker-310m-lite` でその Top-20〜30 件をリランキングし、真に適合度の高い **Top-3〜5 件** を LLM のプロンプトに渡す (レイテンシ: ~2.5秒)

この **2段階ハイブリッドパイプライン** を採用することで、レイテンシと精度の究極のバランスが達成されます。
