# ruri-v3-reranker-310m 包括的ベンチマーク & 批判的考察レポート

本文書では、日本語 Cross-Encoder リランカーモデル [`cl-nagoya/ruri-v3-reranker-310m`](https://huggingface.co/cl-nagoya/ruri-v3-reranker-310m)（ModernBERT-Ja アーキテクチャ、約 315M パラメータ）に対する、**SentencePiece Lite + ONNX Runtime（Zero-Torch 構成）** の性能、推論精度、リソース消費量、およびアーキテクチャ境界におけるトレードオフを客観的に報告します。

---

## 1. 測定環境および構成

- **CPU**: AMD Ryzen / Intel x86_64 (Linux 64-bit, 4 スレッド並列測定)
- **Base Model**: `cl-nagoya/ruri-v3-reranker-310m`
- **Zero-Torch 実装**: `RuriV3RerankerLite` (`dist_assets/ruri_v3_reranker_lite.py`)
- **トークナイザー**: `sentencepiece_lite` 0.1.0 (FlatBuffers `.spm.fb`)
- **推論エンジン**: `onnxruntime` 1.20.1 (FP32 ONNX opset 17)
- **比較対象（公式標準）**: `torch` 2.14.0 + `transformers` 4.49.0 (`AutoModelForSequenceClassification` + `AutoTokenizer`)

## 2. ベンチマーク実測結果

### (1) 多段階モデル（精度・量子化・層剪定）の比較 (CPU 4スレッド実測)

| モデル構成・精度 | 実体サイズ | 配信サイズ (Gzip) | サイズ削減率 | CPU レイテンシ (Top-10) | 速度比 | Top-1 一致率 | 順位一致度 (1〜5位) | 適用領域とトレードオフ |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **FP32 (Original)** | 1,202.6 MB | - | 基準 | 2,589.7 ms | 1.00x | 100% | `[0, 1, 2, 3, 4]` (基準) | 公式同等の完全精度 |
| **FP16 (GPU専用)** | 601.4 MB | - | -50.0% | (GPU専用) | - | 100% | 100% 一致 | Tensor Core GPU (CC ≥ 7.0) 最適化 |
| **INT8 (Linearのみ)** | 526.0 MB | - | -56.3% | 2,072.8 ms | 1.25x | 100% | `[0, 2, 1, 3, 4]` | 線形層のみ動的量子化（境界順位に微小差） |
| **INT8-Full (線形+語彙)** | **301.0 MB** | **202.7 MB** | **-75.0%** (Gzip **-83.1%**) | **2,116.9 ms** | **1.22x** | **100%** | **`[0, 1, 2, 3, 4]` (100% 一致)** | **CPU推奨本流**: 順位完全一致・モデル容量最小化 |
| **Pruned-16L (層剪定)** | **220.6 MB** | **178.1 MB** | **-81.7%** (Gzip **-85.2%**) | **1,382.3 ms** | **1.87x** | **100%** | `[0, 2, 1, 3, 4]` | **低遅延重視**: 16層間引きによる高速化（Top-1維持） |

#### 技術的考察: 量子化と層剪定におけるトレードオフ
- **INT8-Full (MatMul + Gather 量子化)**:
  - 語彙埋め込みテーブル（`Gather`）および全結合線形層（`MatMul`）を動的量子化し、さらに Gzip 圧縮転送を行うことで、**ダウンロードサイズ 202.7 MB** を達成。
  - 実測では FP32 元モデルと **Top-5 ランキング順位が 100% 完全一致** し、認識精度の劣化を極小に抑えています。
- **Pruned-16L (25層中16層の均等間引き)**:
  - 再学習（知識蒸留）を行わず中間層を均等剪定しているため、**レイテンシは約 1.87倍 高速化** します。
  - 検索システムにおいて最も重要な「Top-1 適合ドキュメント」は正確に維持されますが、スコアが僅差の境界ドキュメント（2位と3位の入れ替わり等）では順位変動が生じます。厳密な順位保持が求められる用途では INT8-Full、応答レイテンシが最優先される用途では Pruned-16L の選定が推奨されます。

### (2) コールドスタート & メモリ消費特性 (Threads=4)

| 評価指標 | 公式 PyTorch (Transformers) | Zero-Torch (RuriV3RerankerLite) | 差分・特性 |
| :--- | :--- | :--- | :--- |
| **モデルロード時間** | 5,456.0 ms | **4,534.3 ms** | **約 1.20x 高速** |
| **環境インストール容量** | 約 2.5 GB 超 (PyTorch + CUDA 関連ライブラリ) | **約 70 MB** (Wheel + ONNX Runtime) | **約 97% 削減** |
| **プロセス最大常駐メモリ (RSS)** | 2,392.3 MB | 3,126.9 MB | アリーナ拡張による確保 (+30.7%) |

#### 批判的考察: メモリ消費の要因
- **インストールフットプリント**:
  - Python パッケージの総容量は 2.5GB 超から約 70MB に圧縮されるため、コンテナイメージの軽量化、CI/CD におけるビルド時間短縮、サーバーレス実行基盤のコールドスタート低減に寄与します。
- **実行時プロセス RSS**:
  - ONNX Runtime の `CPUExecutionProvider` は、並列スレッドごとのメモリ再利用効率を高めるためメモリアロケータ（Arena）を積極的に事前確保します。そのため、プロセス常駐メモリ（RSS）は PyTorch より一時的に約 700MB 増加します。極端にメモリ制約が厳しいコンテナ環境では、スレッド数の制限（2〜4スレッド）または `arena_extend_strategy` の調整が必要です。

### (3) RAG Top-N リランキングレイテンシ & スループット (Threads=4, 中文 150文字)

実務の RAG パイプラインにおける候補文書 Top-$N$ 件に対する精密リランキング測定結果です。

| 候補件数 (N) | PyTorch E2E (ms) | Lite E2E (ms) | 高速化倍率 | Lite スループット | トークナイズ単体高速化 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Top-5**   | 567.3 ms | **540.4 ms** | **1.05x** | **9.3 docs/s** | **4.24x 高速** |
| **Top-10**  | 1,104.7 ms | 1,277.4 ms | 0.86x | 7.8 docs/s | **4.51x 高速** |
| **Top-20**  | 2,343.2 ms | 2,479.5 ms | 0.95x | 8.1 docs/s | **4.18x 高速** |
| **Top-50**  | 5,828.6 ms | 6,215.3 ms | 0.94x | 8.0 docs/s | **3.79x 高速** |
| **Top-100** | 11,214.4 ms | 12,452.8 ms | 0.90x | 8.0 docs/s | **4.55x 高速** |

#### ボトルネック要因の分析
- **前処理（トークナイズ）**: `sentencepiece_lite` による C++ ゼロコピーペアトークナイズは、Python ラッパーの `AutoTokenizer` に対し **一貫して約 3.8〜4.5倍 高速** です。
- **行列演算**: 315M パラメータモデルの CPU 推論では、計算時間の大半が行列積（GEMM）に費やされます。小件数（Top-5）ではトークナイズ短縮とディスパッチオーバーヘッドの少なさにより本実装が優位ですが、件数が増加すると Intel MKL 最適化カーネルを持つ PyTorch が同等〜若干先行（約 5〜10% 差）します。

## 5. アーキテクチャ選定指針

### Bi-Encoder と Cross-Encoder の役割分担

実測値の通り、315M パラメータの Cross-Encoder は CPU 4スレッド環境で **1秒間に約 8 ドキュメント** を処理します。
- Top-10 リランキング: **約 1.2 秒**
- Top-50 リランキング: **約 6.2 秒**
- Top-100 リランキング: **約 12.5 秒**

そのため、大規模コーパス（数千〜数十万件）に対して直接 Cross-Encoder を適用することは計算コスト上現実的ではありません。

| 方式 | 代表モデル | 計算量 | 利点 | 制約事項 |
| :--- | :--- | :--- | :--- | :--- |
| **Bi-Encoder (埋め込み)** | `ruri-v3-30m-lite`<br>`ruri-v3-310m-lite` | 事前インデックス: $O(1)$<br>検索: 内積計算 | 数万〜数百万件から **数ミリ秒** で候補を抽出可能 | クエリと文書の相互詳細文脈の捉え漏れ |
| **Cross-Encoder (リランカー)** | `ruri-v3-reranker-310m-lite` | $O(N)$ (リクエスト毎の全結合推論) | 全レイヤーで Cross-Attention するため高い検索適合率 | 候補件数 $N$ に比例して推論計算コストが増加 |

### 推奨パイプライン（2段階検索システム）
1. **第 1 段階 (粗選定)**: `ruri-v3-30m-lite` で大規模インデックスから **Top-20〜30 件** を高速抽出 (レイテンシ: < 10ms)
2. **第 2 段階 (精密選定)**: `ruri-v3-reranker-310m-lite` (INT8-Full または Pruned-16L) で **Top-3〜5 件** にリランキングして LLM 等の後続処理へ渡す (レイテンシ: 約 1.3〜2.5秒)
